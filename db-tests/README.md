# Migration 001 tests

These are the suites that checked Migration 001 before it went live: 472 checks across access, booking, staff, review and round-8 behaviour, plus every one of the 6,480 price combinations (`m001_tests_pricing.sql`, generated by `gen_pricing_matrix.py`).

They were run in two places:

- **The test project ("Alchemist Test"),** pasted into its SQL Editor after the migration. That's the reliable way to re-run them: they need Supabase's real Auth and Storage schemas.
- **A local Postgres 16** in the cloud workspace where this was built, with Supabase's schemas stubbed. The shell scripts (`run_local.sh`, `concurrency_local.sh`, the `dryrun_*` scripts) still point at that machine: `PGHOST=/home/claude/.pgtest`, port 54329. Set `PGHOST`, `PGPORT` and `PGUSER` for your own Postgres before using them.

Order that passes: `m001_framework.sql`, `m001_fixtures.sql`, then the `m001_tests_*.sql` suites; run the concurrency script once, on its own database.

## Migration 002 tests (Oct 5, 2026)

- `m002_tests_conditions.sql`: the condition fees, the steam rule, the WetGloss minutes, the mandatory condition choice and the Review lane for "Other". 37 checks, all passing on the test project.
- `m002_tests_pricing.sql`, generated by `gen_pricing_matrix_m002.py`: the price matrix with conditions (the inputs are built on the server in the generator's order; only the expected results are listed, so the file stays small enough for the SQL Editor).

- `m002_tests_reviews.sql`: reviews (Migration 002 part 5): 18 checks, all passing on the test project. Run after `m002_tests_conditions.sql`.

## Migration 003 and 004 tests (Oct 5 and Oct 11, 2026)

## Migration 008 tests (Nov 7, 2026)

- `m008_tests.sql`: Migration 008 (doc 45, the owner's answers 1, 3 and 5). Start only on the job's own day and Complete on that day or later, Parker's date (a future and a past job refused with the day in the message; today, a job started on an earlier day, and a confirmed job never started all complete), the functions' grants and settings unchanged; the owner's address column closed to every API role (the admin included) while the other 28 settings columns stay readable, and `shop_address_on_file()` for the admin only; `my_bookings` (part 3): a manager who books and confirms a "Come to us" job for themselves gets no address, with or without the authenticator, while a customer, a detailer and the admin still get it on their own confirmed booking, and each booking carries its conditions. 40 checks, all passing on the test project. One DO block; it never reads the address itself (part 3 sets a placeholder inside its rolled-back blocks and checks only whether one comes back).
- Since Migration 008 starts and completes a job only on its day, the three suites that did so on a later date move the booking to today first (`m001_tests_staff.sql` b1, `m001_tests_x_review.sql` r1 with its shortening checks on that day, `m002_tests_reviews.sql` m002a), and `m001_tests_staff.sql` stores the address with `returning 1`, since no API role reads it back.
- The Migration 001 suites predate the later migrations (buffers, closures, condition fees), so on a database with all of them about 30 of their checks fail whatever the date; they are compared before and after a change, not counted as a pass.
